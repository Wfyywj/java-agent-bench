# Java 工程 Agent 任务目录设计

## 当前交付与可信边界

`catalog/tasks.json` 是 **25 题原创设计目录，不是 25 题已可运行 benchmark**。每题均为 `design_only`。本批交付包含 140 条验收要求、任务级风险、加权 rubric、基础设施需求和客观测试策略；不包含实际业务服务、故障夹具、隐藏验收器或参考补丁。任何其他文档中单独实现的 pilot 不会自动使本目录对应题目成为 runnable。

所有业务组织、事故、政策和数据均为原创虚构场景，未复制第三方仓库问题或未获授权的生产事故。Java 21 是计划运行目标，不代表已验证依赖兼容性。没有模型排名、成功率、token 成本、耗时或实测难度结论。难度名称是便于组织工作的暂定标签。

## 为什么不是算法题集合

任务要求同时处理业务语义与工程证据：需求冲突可能需要暂停危险操作；跨仓调用链决定改动范围；重试、取消和迁移中间态决定正确性；测试应能够推翻错误实现；审查需有可运行反例；事故分析需排除替代假设。不能仅凭生成代码、文档长度或单元测试数量获得高分。

目录覆盖：需求澄清、跨仓定位、实现、测试、代码审查、事故诊断。某些任务复合多个轴；`category` 表示主任务形态，`environment.skillAxes` 表示实际能力组合。

## 五档边界与题目索引

| 暂定层级 | 主要复杂性 | 题目 |
|---|---|---|
| bronze / 青铜 | 单服务内真实契约、边界与最小证据 | B01 时间窗澄清；B02 归还幂等；B03 稳定分页；B04 报价审查；B05 资源泄漏诊断 |
| silver / 白银 | 多模块或少量仓库、事务/授权/兼容边界 | S01 乱序退款；S02 资格协议升级；S03 异步导出授权；S04 批次取消；S05 慢查询 |
| gold / 黄金 | 多仓异步流程、恢复路径、独立推理 | G01 库存预占；G02 历史计费；G03 离线上传；G04 权限缓存审查；G05 线程池饥饿 |
| diamond / 钻石 | 系统级迁移、模型测试或复杂事故 | D01 在线分片；D02 模型化预约测试；D03 缓存积压事故；D04 插件隔离；D05 可恢复发券 |
| king / 王者 | 全链路交付、联合故障与政策/发布治理 | K01 账本容灾；K02 隐私删除；K03 计费替换；K04 联合故障恢复；K05 结算完整闭环 |

分层不是“仓库越多分越高”。主要参考独立交互约束数量、错误影响、状态空间、恢复难度和所需证据链长度。pilot 后若低档任务比高档更难，应调整标签而不是修改实测数据；必须保留目录版本与重分类理由。

## JSON 字段契约

顶层为任务数组，不包含额外 wrapper。每题使用相同的 13 个顶层键：

| 字段 | 结构与含义 |
|---|---|
| `id` | B01–B05、S01–S05、G01–G05、D01–D05、K01–K05；稳定身份，不复用删除 ID |
| `title`, `summary` | 中文名称与真实业务问题摘要 |
| `tier` | `bronze` / `silver` / `gold` / `diamond` / `king` |
| `category` | 主任务形态标识；不作为严格互斥能力标签 |
| `brief` | `context`、`mission`、`constraints`、`inputPackagePlanned`；明确哪些输入尚待实现 |
| `deliverables` | 所需提交产物列表；依据任务类型提交实现、审查或诊断证据 |
| `acceptance` | 对象数组：`id`、`criterion`、`method`、`critical`；每题 5–6 条，ID 与评分证据映射 |
| `risks` | `failureCases`、`traps`、`invariants`、`criticalFailurePolicy` |
| `rubric` | 对象数组：`dimension`、整数 `weight`、`evidence`；每题权重合计 100 |
| `environment` | 运行目标、基础设施、计划资产、客观测试策略、技能轴、网络策略和预算状态 |
| `status` | 本版本全部 `design_only` |
| `difficultyRationale` | 暂定分层理由及未实测声明 |

`acceptance.method` 提供统一评估渠道，具体实验步骤由 `environment.objectiveTestStrategy` 定义。`risks.invariants` 摘录两个核心要求，并不意味着其余验收要求可以忽略。`critical=true` 的条目用于不可被高平均分抵消的核心失败判定；正式实现前应拆分复合条目为细粒度隐藏断言，避免一条部分通过却无法解释扣分。

## 客观评测，不靠“看起来合理”

1. **固定输入**：每题锁定 starter 提交、依赖、容器、数据 seed、接口契约及允许工具。参考实现和候选实现使用同一预算。
2. **独立 oracle**：资金、库存、权限和数据生命周期使用独立模型，不能复用被测业务函数。历史系统有已知缺陷时，旧系统不是唯一真值。
3. **边界可控**：Clock、调度屏障、故障钩子、消息重排、代理和模拟存储用于产生确定性失败；尽量避免依赖 sleep 与偶发压测。
4. **故障断点**：区分外部成功/本地提交/响应丢失。每个持久化边界均明确应保留、重试或补偿的状态。
5. **证据核对**：状态、日志、测试报告、变更位置都映射到验收 ID。审查任务需位置、反例、影响与政策依据，并对误报扣分。
6. **反作弊边界**：验收器在隔离进程/容器和独立工作区；Agent 不能编辑 oracle、保留用例和分数文件。候选测试只作补充证据，不能自行决定最终通过。
7. **预算一致**：性能先测查询次数、队列界限、资源释放等结构性指标；绝对延迟只在固定机器和负载下比较。目录没有未经校准的绝对耗时目标。

隐藏用例不是“隐瞒需求”：业务规则应公开；仅隐藏数据组合、故障位置与输入变体。澄清题需要预先冻结答复手册，所有被测 Agent 可获得同等答复；关键问题缺失时应奖励明确阻断，而不是奖励猜中隐含政策。

## 评分草案

每个维度使用 0、0.5、1 三档证据锚点乘以权重：缺失/不可复现；部分有效但关键边界遗漏；完整且可复演。正式 pilot 可扩为细粒度断言，须版本化。定性判断采用双人独立复核，分歧留下裁决记录。

任务分为加权维度分与 `task_pass` 两个结果：核心条目被证实违反时 `task_pass=false`，仍报告真实维度分。尚未执行或基础设施失败时标记 `not_evaluated` / `infrastructure_error`，不得计作模型失败或通过。没有实测前不设置宣传性通过阈值或段位晋升线。

必须单列：业务正确性、异常/恢复、跨仓证据、交付完整性。编译成功不是业务通过；自报“所有测试通过”不是执行证据；整体全绿也不证明生产安全。

## 从 design_only 到可运行任务的准入清单

- [ ] 原创 starter、许可与依赖来源核对完成，仓库提交固定。
- [ ] 业务规则及澄清答复手册冻结；允许假设与必须阻断的歧义明确。
- [ ] 合成数据、协议桩及所有基础设施可从空环境重建，无真实凭据。
- [ ] 已知错误版本能在公开/保留测试中失败，参考补丁能通过；不能只验证“测试跑完”。
- [ ] 独立验收器和 oracle 与候选改动隔离，故障 seed 可重放。
- [ ] 所有 acceptance ID 映射到实际断言或明确的人工评分锚点。
- [ ] 本机与干净 CI 至少完成一次重建；记录环境、命令、退出码和产物。
- [ ] 超时、内存、CPU、网络和依赖缓存策略经 pilot 校准。
- [ ] 对模型执行失败、任务歧义与基础设施失败分别归因。
- [ ] 仅对已满足准入条件的题目更新状态，并附证据链接和版本；不得批量升级整层级。

后续目录若引入状态枚举，应与实际 schema 一起版本化。当前只保证 `design_only`，不预先承诺其他状态的实现。

## 首批实现建议

优先 B02、B03、S01：分别建立真实事务、稳定查询与事件状态机的可重用隔离验收能力。随后实现 G01 以证明多服务故障注入能力，再推进高档迁移和联合故障。该顺序是建设建议，不是额外已完成工作，也不替代父项目的优先级决策。
